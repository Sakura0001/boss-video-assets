# 主动招呼两段话术与后续状态调整设计

## 目标

把原第一段和第二段压缩为一段用户批准的技术与岗位介绍，把原第三段替换为用户批准的匹配与转投提示，并取消附件简历请求动作。平台默认招呼之后只发送两段固定纯文本。

## 固定文案

第一段必须逐字发送以下纯文本，不使用 Markdown，不拆分，不扩写：

`我们团队正在探索AI时代的下一代智能应用，围绕大语言模型（LLM）、AI Agent、RAG、知识增强、智能工作流和多Agent协同，打造能理解任务、主动分析并自动执行的企业级应用。目前已覆盖智能助手、自动化决策、智能分析、企业知识管理和AIOps等场景，加入后可参与从模型应用设计、Agent架构搭建到生产落地的完整流程，积累AI时代的核心技术能力。`

第二段必须逐字发送以下纯文本，不使用 Markdown，不拆分，不扩写：

`我看了一下你的背景和在线简历，和我们AI应用研发方向有一定匹配度。欢迎你了解一下我们的技术方向和发展机会。我们这边相对wlb一些，自盈利部门，年终奖可以保证，日常加班可以随意申报，也不会强制要求来。部门整体氛围好，新老员工无断层现象，跳槽到外面的员工都有很大幅度的涨薪，不需要担心个人竞争力。如果你现在已投递的话，也开始对比下现在投递的部门，看是否想转投，现在还可以转，后面正式进流程就没办法在转投了`

保留用户原文中的“在转投”写法，不自行润色。

## 流程变化

1. Boss 平台默认招呼成功后，在同一个精确会话中依次发送两段固定纯文本。
2. 第二段发送并读回验证成功后，不执行 `request-attachment-resume`，也不使用 `--request-resume`。
3. 候选人状态从 `greeted` 更新为 `waiting_application_status`，不再更新为 `waiting_resume`。
4. 候选人后续主动发送附件简历时，现有附件接收、验证和评估流程继续有效。
5. 历史候选人状态和运行数据库不迁移、不重写。
6. 第二段属于机会介绍，不代表候选人已经具备转投资格，也不计作一次到期投递状态追问；候选人回复后仍须按现有四字段规则运行 `evaluate-transfer`。
7. “在线简历”仅指推荐页当前可见的候选人资料，不新增会消耗平台权益的 `boss preview`。

## 业务来源与代码范围

- 先更新已安装源技能中的固定话术、主动招呼步骤、状态机和语气说明。
- 更新 Python 执行器的知识库标题、两消息数量约束及成功后的状态写入。
- 更新 Boss CLI 的消息序列约束，使 `send-sequence` 接受且只接受两条消息。
- 更新执行器与 CLI 测试，锁定新文案、两段发送顺序、无附件请求参数和新状态。
- 通过源技能同步脚本生成仓库 `skills/boss-zhaopin/` 镜像，不直接维护镜像。

## 错误处理与安全边界

- 两段中的任意一段发送或验证失败时，保持现有立即停止规则，不继续状态流转。
- 平台招呼已确认后若消息发送中断，保留 `greeted` 和长期去重；普通重跑不会重复触达，恢复前必须人工打开精确会话核对。
- 不增加额外消息；greet-only 不处理未读聊天或到期跟进，也不启动主动招呼任务。
- `--validate-only` 只读校验配置并报告两条消息，不获取执行锁、不初始化或清理状态，也不调用 Boss 命令。
- 不修改求职期望黑名单、学校、学历、毕业年份、专业和去重规则。
- 新转投文案不得绕过现有投递部门、心理测评、笔试和面试门槛；只有 `evaluate-transfer` 返回 `exchange_wechat` 才能继续交换微信。

## 验证标准

- 知识库读取结果与两段用户批准文案逐字一致，且均为纯文本。
- 执行器只调用一次两消息序列，不携带附件简历请求行为。
- 两条消息验证成功后写入 `waiting_application_status`。
- 源技能运行时测试、技能契约测试和快速校验全部通过。
- 同步后的仓库镜像与源技能一致，仓库测试通过。
